# Operations, Performance, and Capacity

- **DB-131** — Monitor availability, latency, throughput, errors, saturation, replication lag, storage growth, locks, deadlocks, cache efficiency, and backup health.
- **DB-132** — Establish workload-specific performance baselines and alert thresholds before production release.
- **DB-133** — Track slow queries and plan regressions with normalized query fingerprints.
- **DB-134** — Query optimization must use execution plans and measured evidence rather than intuition alone.
- **DB-135** — Statistics, vacuuming, compaction, index maintenance, and integrity checks must be automated and monitored.
- **DB-136** — Connection pools must have bounded sizes, acquisition timeouts, health validation, and leak detection.
- **DB-137** — Pool sizing must account for total application instances and database concurrency capacity.
- **DB-138** — Applications must apply command timeouts and release connections promptly.
- **DB-139** — ORMs must use explicit loading, projection, pagination, batching, transaction, and concurrency behavior.
- **DB-140** — ORM-generated SQL must be reviewed for critical and high-volume paths.
- **DB-141** — Capacity planning must forecast data, index, log, backup, memory, CPU, I/O, connection, and maintenance growth.
- **DB-142** — Storage exhaustion thresholds must leave enough time for safe remediation.
- **DB-143** — Production maintenance must use approved change, communication, rollback, and validation procedures.
- **DB-144** — Every critical database must have an owner, support model, escalation path, runbook, and dependency map.
- **DB-145** — Database incidents must produce evidence-based corrective actions for schema, query, capacity, configuration, process, or architecture weaknesses.
