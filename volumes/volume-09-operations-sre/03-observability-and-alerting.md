# Observability and Alerting

- **SRE-041 — Telemetry Coverage:** Critical services MUST emit sufficient logs, metrics, and traces or equivalent telemetry to diagnose user-impacting failures.
- **SRE-042 — Structured Logs:** Production logs SHOULD be structured and consistently include timestamp, severity, service, environment, and correlation context.
- **SRE-043 — Sensitive Data Logging:** Secrets, credentials, tokens, and unnecessary personal data MUST NOT be logged.
- **SRE-044 — Correlation IDs:** Distributed request paths SHOULD propagate correlation or trace identifiers across service boundaries.
- **SRE-045 — Golden Signals:** Critical services SHOULD monitor latency, traffic, errors, and saturation or equivalent domain signals.
- **SRE-046 — Dependency Metrics:** Critical dependencies MUST have observable health or measurable failure indicators.
- **SRE-047 — Dashboard Purpose:** Every production dashboard SHOULD answer a defined operational question rather than display uncurated metrics.
- **SRE-048 — Source of Truth:** Alert and dashboard queries MUST reference documented telemetry sources and definitions.
- **SRE-049 — Alert Actionability:** Paging alerts MUST require a timely human action; informational conditions SHOULD not page.
- **SRE-050 — Symptom Before Cause:** Paging SHOULD prioritize user-impacting symptoms over speculative internal causes.
- **SRE-051 — Alert Ownership:** Every active alert MUST have an owner and an associated response path.
- **SRE-052 — Runbook Linkage:** Actionable alerts SHOULD link directly to relevant dashboards and runbooks.
- **SRE-053 — Severity Mapping:** Alert severity MUST be mapped consistently to service impact and response urgency.
- **SRE-054 — Deduplication:** Alerting systems SHOULD suppress duplicate signals that represent the same incident.
- **SRE-055 — Noise Control:** Noisy alerts MUST be tuned, removed, or downgraded rather than normalized as unavoidable noise.
- **SRE-056 — Flap Control:** Repeated transient state changes SHOULD use appropriate evaluation windows or hysteresis.
- **SRE-057 — Missing Telemetry:** Absence of expected telemetry from critical components SHOULD be detectable.
- **SRE-058 — Synthetic Checks:** Critical user journeys SHOULD use synthetic or equivalent external checks where feasible.
- **SRE-059 — Monitoring From User Perspective:** At least one key availability signal SHOULD originate outside the service process itself where practical.
- **SRE-060 — Time Synchronization:** Systems participating in incident diagnosis MUST use reliable clock synchronization.
- **SRE-061 — Retention:** Telemetry retention MUST align with investigation, security, compliance, and cost requirements.
- **SRE-062 — Access Control:** Production telemetry MUST enforce appropriate access control because logs and traces may contain sensitive operational context.
- **SRE-063 — Alert Testing:** Critical alert paths MUST be periodically tested, including delivery to on-call responders.
- **SRE-064 — Monitoring as Code:** Alert and dashboard configuration SHOULD be version-controlled where supported.
- **SRE-065 — Observability Review:** Major architecture changes MUST review whether existing telemetry remains sufficient for diagnosis and SLO measurement.
